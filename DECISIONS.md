# Decisions and assumptions

1. **Item matching.** A supplied item code is authoritative when it exists in the item master. Otherwise, normalized description-token overlap is used with a small generic abbreviation map (`brg` → `bearing`, `hyd` → `hydraulic`). A confident unique match is accepted; unresolved or ambiguous batch descriptions follow the new-item path because there is no interactive clarifier in a batch. Chat asks for clarification.
2. **New items.** Unmatched batch descriptions are treated as new items and never clubbed. If the requester estimate is missing, the line is routed as `NOT_PROCESSED` with a reason; no invented estimate is used.
3. **Clubbing.** Known items club only when item and plant match, the creation date is within 14 calendar days of the group's first line, and the need-by date is within seven days of the first line. When more than one group qualifies, the earliest is selected.
4. **Units.** Quantity totals assume all lines for an item use a compatible unit. The app uses the item-master unit for matching and does not convert different units.
5. **Requirement date.** The first line's creation date is used for policy, contract, and history checks. Chat requests use the local server date when their first message arrives.
6. **Contract ceiling.** Registered consumed values are the starting point. New requirements consume ceiling in requirement-date order. Contracts found only in signed PDFs start at zero, as stated in the policy.
7. **PDF contracts.** The engine attempts to read schedule rows, dates, supplier ID, and ceiling using pypdf. If a PDF is image-only or its layout differs, a buyer must add/normalize it manually; extraction can fail visibly.
8. **Preferred supplier ranking.** The explainable score is `10 × PO count + 20 × recency + 15 × contract flag + 0.2 × on-time percentage + 3 × quality rating`. Recency is 1 for a PO within 90 days, 0.5 within 365 days, and 0 otherwise. Only active suppliers are ranked or suggested.
9. **Sourcing top-up.** Preferred suppliers are used first; remaining slots are filled with active suppliers listing the item's category, ordered by on-time delivery, then quality, then supplier ID.
10. **Policy conditions.** Rules are evaluated in JSON list order; the first matching rule wins. The condition evaluator supports `equals`, `less_than`, `less_than_or_equal`, and `greater_than_or_equal` against named request facts such as category and plant.
11. **Amendment workflow.** PDF policy text is extracted locally. A buyer translates the amendment into the policy JSON structure, previews the clause changes, and explicitly activates the version. This makes rule changes data-driven, but the app does not infer arbitrary natural-language clauses automatically.
12. **Chat memory.** Chat request details are held in browser memory for one request and disappear when the page reloads. Batch runs and buyer actions are persisted in SQLite.
13. **Free hosting.** The free demo may sleep and local files may be reset by a restart. Re-import task data and policy after restart; use this as an assessment demo, not production procurement software.
14. **Preferred-supplier export.** Only the three highest-ranked active suppliers are exported per item. The score factors and each supplier's factor summary are included so a buyer can inspect the ranking.
15. **Buyer approval.** Approval records a PO reference for PO decisions and creates an RFQ, RFP, or sourcing reference for sourcing decisions. These are local app records; the prototype is not connected to an ERP or external purchasing service.
16. **Buyer override.** An override changes the displayed/exported route and decision and records the original route plus the buyer's written reason, actor, and timestamp. A buyer must check supplier and price fields for consistency after changing a route.
